# MusicXML → OpenSongChart: License & Library Findings

Status: active (research findings recorded; implementation phases 1–7 open, tracked as beads)
Id: musicxml-support

This document captures findings from an exploratory look at adding MusicXML conversion support: whether it has license impacts, and whether an existing MusicXML library is worth using vs. hand-rolling a parser.

---

## License Impact

- This project (`PsarcChartCore`) is `GPL-3.0-or-later` (root [LICENSE](../../LICENSE), and declared via `PackageLicenseExpression` in [PsarcChartCore.csproj](../../PsarcChartCore/PsarcChartCore.csproj)).
- All current dependencies (OpenSongChart, PsarcUtil, Rocksmith2014PsarcLib, BnkExtractor, Pfim) are MIT — freely compatible with GPL.
- The MusicXML format itself is an openly published XML schema, not under a restrictive license — implementing a reader/writer against the XSD carries no license concern of its own.
- The only license risk would come from pulling in a third-party MusicXML library whose license isn't MIT/BSD/Apache-compatible. The one live .NET option (below) is BSD-2-Clause, which is fine.

**Conclusion: no license impact**, regardless of whether the implementation hand-rolls the parser or uses the existing BSD-licensed library.

## Existing MusicXML Libraries

| Library | License | Status | Scope |
|---|---|---|---|
| [MusicXml.NET](https://github.com/vdaron/MusicXml.Net) (vdaron) | BSD-2-Clause | .NET Standard 2.1, last pushed 2024-08, 67★, 3 open issues | Read-only parser |
| [Bob-Eeckhout's fork](https://github.com/Bob-Eeckhout/MusicXml-dotnet-customized) | same base | Undocumented personal fork, no README detail on what changed | Unclear scope |
| [hedgetechllc/musicxml](https://github.com/hedgetechllc/musicxml) | MIT, full read+write | Active, claims to implement the full standard | **Rust**, not .NET — would need FFI |

MusicXml.NET is the only realistic pre-built .NET option.

### Why it doesn't fit this conversion

Its domain model (`MusicXml/Domain/`) covers `Score/Part/Measure/Note/Pitch/Clef/Key/Time/Tie/Lyric/Backup/Forward`. Reading [Note.cs](https://raw.githubusercontent.com/vdaron/MusicXml.Net/develop/MusicXml/Domain/Note.cs) directly confirms there is **no `Notations`/`Technical`/`Articulations` support at all** — it never parses MusicXML's `<notations><technical>` block.

That block is exactly where MusicXML encodes `<string>`, `<fret>`, `<bend>`, `<hammer-on>`, `<pull-off>`, `<slide>`, `<harmonic>`, palm-mute, tap, etc. — the source for almost every field on [SongFormat.cs](../../Dependencies/OpenSongChart/SongFormat/SongFormat.cs)'s `SongNote` (`Fret`, `String`, `HandFret`, `SlideFret`, `CentsOffsets`, and most of `ESongNoteTechnique`). The library only covers pitch/duration/tie/lyric/measure — the skeletal, easy part — and leaves the guitar-tab-specific data unparsed. It's also read-only, and its model types use `internal` setters, so extending it means forking rather than just consuming the NuGet package.

## Recommendation (superseded — see below)

The original conclusion was to hand-roll a parser against the MusicXML XSD in C#, evaluated only against the .NET ecosystem (`PsarcChartCore`). That evaluation missed that this repo's actual multi-format conversion pipeline lives elsewhere and already solves this exact problem for a comparable format.

Since `<notations><technical>` would need to be hand-parsed either way, using MusicXml.NET only buys the note/pitch/duration bookkeeping while still requiring a second hand-written pass over the same XML for techniques — not much saved for the cost of carrying an under-maintained, internal-setter-locked dependency. That reasoning still holds; the correction below is about *where* and *how* the conversion should live, not a reversal of the MusicXml.NET verdict.

## Revised Recommendation: reuse alphaTab, don't hand-roll

[SongConverter](../../SongConverter) is a browser-based (Vite/TypeScript) converter, not a C#/PsarcChartCore feature. Its Guitar Pro path ([gpConverter.ts](../../SongConverter/src/gpConverter.ts)) already delegates all `.gp3/.gp4/.gp5` parsing to [alphaTab](https://github.com/CoderLine/alphaTab) (MPL-2.0, already a `SongConverter` dependency — see [package.json](../../SongConverter/package.json)) and only maps alphaTab's `Score/Track/Staff/Bar/Voice/Beat/Note` object model onto `SongInstrumentNotes`/`SongNote`.

alphaTab **also ships a MusicXML importer** (plain `.musicxml`/`.xml` and compressed `.mxl`), reached through the same `ScoreLoader.loadScoreFromBytes()` entry point `gpConverter.ts` already calls. It parses MusicXML `<notations><technical>` (string, fret, bend, hammer-on/pull-off, slide, tap) directly into the *same* `Note`/`Beat` fields (`note.fret`, `note.hasBend`, `note.isHammerPullDestination`, `note.slideOutType`, etc.) that [buildNote()](../../SongConverter/src/gpConverter.ts) in `gpConverter.ts` already reads for GP files. alphaTab's own [MusicXML coverage page](https://alphatab.net/docs/formats/musicxml/) claims 62% of the MusicXML 4.0 spec (52% of "relevant" features), but reading the importer source directly (Phase 1 below) found that page's per-feature checklist doesn't fully match the code — some gaps it claims (vibrato) are actually handled, and some things it claims are handled (harmonic type) currently aren't. The source-verified picture, not the docs page, is what the phases below are based on.

This means the MusicXML → OpenSongChart conversion is not a new parser at all — it's a thin new entry point that feeds MusicXML bytes into the parser this project already trusts, plus generalizing `gpConverter.ts`'s already-format-agnostic core (it was only ever GP-specific by name) and handling the technique fields MusicXML import leaves unpopulated.

## Implementation Phases

### Phase 1 — Validate real-world coverage before committing to the approach

The 62%/52% coverage figures are against the MusicXML *spec*; what matters is coverage against files real users will actually upload (MuseScore exports, Guitar Pro's "Export to MusicXML", TuxGuitar, Sibelius/Finale/Dorico). Those tools disagree on how they encode the same concepts (e.g. palm-mute and slap/pop have no formal MusicXML element and are usually free-text `<other-technical>` or `<technical><other-technical>` content, which every tool spells differently or omits).

**Findings**, from reading alphaTab's actual importer source ([`MusicXmlImporter.ts`](https://github.com/CoderLine/alphaTab/blob/develop/packages/alphatab/src/importer/MusicXmlImporter.ts), `develop` branch — the docs page's coverage checklist turned out to disagree with the code in both directions, so the source is the ground truth used below, not the page):

- **Tuning/`isStringed` (line 1857, `_parseStaffTuning`):** `staff.tuning`/`showTablature` are populated only from `<staff-details><staff-tuning>` (per-string `tuning-step`/`tuning-alter`/`tuning-octave`) or a `<clef sign="TAB">` (line 1935). Neither is guaranteed present — a file exported as standard notation only (no tab staff) has no tuning data at all, and `staff.isStringed` is a getter over that same tuning array. **Still needs real files**, but the trigger condition is now precise: does a given tool's "export with tab" option actually emit `<staff-tuning>`?
- **Palm-mute: two separate code paths, and the more promising one was missed on the first pass.** `_parsePlay` (line 2868) reads `<play><mute>palm</mute></play>` inside `<sound>` — a formal MusicXML 3.0+ playback element a [MuseScore forum thread](https://musescore.org/en/node/293227) says tools "have generally not been adopted." But there's a second, independent path: `<direction><direction-type><words>P.M.</words></direction-type><direction-type><dashes type="start"/></direction-type></direction>` — a text label followed by a dashed line — sets `beat.isPalmMute = true` for every beat until a matching `type="stop"` (`MusicXmlImporter.ts` lines 2130-2140). This is exactly the "drawn line/text" mechanism the MuseScore thread says tools actually use, and **empirically confirmed working** (Phase 1's dedicated test below): `beat.isPalmMute` came back `true` for both notes under the dashes span. `gpConverter.ts`'s `buildNote()` already reads `note.isPalmMute || beat.isPalmMute` — so this path, not the `<sound>` one, is the real-world-relevant route, and it works. Caveat: the match is a literal, case-sensitive string comparison against `<words>` text (`'P.M.'` exactly) — untested whether MuseScore/Guitar Pro/etc. emit that exact string vs. `"P.M"`, `"palm mute"`, or similar variants; that part still needs real tool-exported files.
- **Slap/pop:** confirmed absent from the importer entirely (no case, not even a commented-out "not supported" placeholder, unlike most other gaps in this file). This tracks with MusicXML itself having no standard element for bass slap/pop — it's a format-level gap, not just an alphaTab one. A text-annotation fallback (Phase 5) is the only route.
- **Harmonic:** `_parseTechnical`'s `case 'harmonic': break;` (line 3556) is a confirmed no-op — nothing is read from the child elements of `<harmonic>` (natural/artificial/touching/pinched), and no `note.isHarmonic`/`harmonicType` assignment exists anywhere in the file. This is a firmer gap than the docs page's "⚠️ reading only" suggested — currently it reads nothing.
- **Vibrato:** contrary to the docs page's "NOT supported," the source sets `note.vibrato = VibratoType.Slight` from two places: the `smear` technical element (line 3606) and a bare `<wavy-line>` ornament not part of a trill (line 3736). `<wavy-line>` is the standard MusicXML idiom for a vibrato line over a guitar note, so this is likely to work for a meaningful share of real files.
- **Dead/muted notes (`FretHandMute`):** [alphaTab issue #2866](https://github.com/CoderLine/alphaTab/issues/2866) (open as of this writing) confirms `<notehead>x</notehead>` — the standard MusicXML way to mark a muted/dead note — is *not* imported as a dead note; the fret number is drawn and sounds normally instead. This directly undermines the `FretHandMute` flag (mapped from GP's `note.isDead`, per `gpConverter.ts`), independent of Phase 1's other findings.
- **Crash risk:** no evidence found of hard parse failures on well-formed files — the open issues found (#2850, #2859, #2861, #2866) are all feature/accuracy gaps, not exceptions. `readScore()` (line 236) wraps the initial XML parse in try/catch and rethrows as `UnsupportedFormatError`, which `ScoreLoader` already handles gracefully (see Phase 4).

**Cross-validation against a second, independent MusicXML parser.** [OpenSheetMusicDisplay](https://github.com/opensheetmusicdisplay/opensheetmusicdisplay) (evaluated separately as a library option — see "Existing MusicXML Libraries" below) parses MusicXML independently of alphaTab, including guitar tab. Grepping its reader source ([`VoiceGenerator.ts`](https://github.com/opensheetmusicdisplay/opensheetmusicdisplay/blob/develop/src/MusicalScore/ScoreIO/VoiceGenerator.ts), [`InstrumentReader.ts`](https://github.com/opensheetmusicdisplay/opensheetmusicdisplay/blob/develop/src/MusicalScore/ScoreIO/InstrumentReader.ts)) for the same elements gives a second opinion on which gaps are alphaTab-specific vs. ecosystem-wide:
  - **Harmonic/slap/pop/palm-mute: zero matches in OSMD either.** Two independently-written, actively-maintained parsers both skip the same elements — meaningfully stronger evidence these are genuinely under-implemented (or, for slap/pop, absent from the format) across the open-source MusicXML ecosystem, not an alphaTab blind spot specifically.
  - **Hammer-on/pull-off: the raw element is corroborated as standard (both libraries read it) — but see the empirical correction below.** OSMD parses `<technical><hammer-on>/<pull-off>` too (`VoiceGenerator.ts` lines 225, 229), confirming it's a genuinely standard, commonly-implemented element, not an alphaTab incidental. This cross-validation only checked that both libraries *attempt* to read the element, though — it doesn't say whether either one's final output actually reflects it. Running real files empirically (below) found alphaTab's does not.
  - **Dead notes: the gap is more precisely alphaTab's own translation step, not a missing-from-the-format issue.** Both libraries correctly read the `<notehead>` *shape* — alphaTab maps `'x'` to `MusicFontSymbol.NoteheadXBlack` (line 3185 of `MusicXmlImporter.ts`) exactly like OSMD builds a `Notehead(note, shape, filled)` object from the same element (`InstrumentReader.ts` lines 453-454, 517-518). Neither library makes the further semantic leap from "X-shaped notehead" to "mute this note, cut its duration short" — OSMD has no reason to (it's a renderer with no such gameplay concept), and alphaTab *has* that concept (`isDead`, inherited from its GP-native model) but a repo-wide grep for `isDead` inside `MusicXmlImporter.ts` returns zero matches — the notehead-shape branch never sets it. So OSMD confirms the raw shape data is standard/parseable; the gap is specifically alphaTab's own shape→semantics wiring, tracked as #2866.

**Empirical verification against real files.** The W3C Music Notation Community Group (the body that now stewards MusicXML) maintains an [MIT-licensed test suite](https://github.com/w3c-cg/musicxmlTestSuite) of real, small, spec-conformant `.musicxml` files — a legitimate direct resource, not song content, safe to test against. Two files were downloaded and run through `alphaTab.importer.ScoreLoader.loadScoreFromBytes()` in a throwaway Vitest test using the project's actual installed dependency (`@coderline/alphatab@1.8.4` — confirmed the tagged `v1.8.4` source matches what was read from `develop` for everything below, so this isn't a version-drift artifact):

- **[`71e-TabStaves.musicxml`](https://github.com/w3c-cg/musicxmlTestSuite/blob/master/xmlFiles/71e-TabStaves.musicxml)** (8 fretted-instrument parts: 4×guitar, bass, banjo, lute, ukulele, each with `<staff-tuning>`): `isStringed`, `showTablature`, and `staff.tuning` all came back correctly for every part (e.g. track 0's tuning `[64,59,55,50,45,40]` is exactly standard guitar E2-E4 in MIDI numbers), and every note's `fret`/`string` matched the source (`fretStringCount === noteCount` for all 8 tracks, including the 1-indexed→0-indexed and low-to-high string reversal). **This resolves the Phase 1 tuning/`isStringed` question, at least for one authoritative "does it work at all" case: when a file does carry `<staff-tuning>`, it comes through correctly.** Part names were plain instrument names ("Guitar" ×4, "Bass Guitar", "Banjo", "Lute", "Ukulele") with no lead/rhythm/role hints — direct evidence for Phase 2's role-detection concern below.
- **[`32a-Notations.musicxml`](https://github.com/w3c-cg/musicxmlTestSuite/blob/master/xmlFiles/32a-Notations.musicxml)** (a self-documenting file covering the full `<notations>` family, each note's expected effect spelled out in its own `<lyric>`): confirmed **bend** (`hasBend: true` for all 4 bend variants — regular, with-bar, pre-bend, release), **tap** (`tap: true`), and **vibrato** (`vibrato: 1/Slight` on the `<wavy-line>` note) all work exactly as the source reading predicted. Confirmed **harmonic is a total no-op empirically**, not just in theory — all 15 harmonic-labeled notes (natural, artificial, with base/touching/sounding pitch combinations) came back `isHarmonic: false`.
- **A real, unexpected finding source-reading missed: hammer-on/pull-off does not survive to the final `Score`, contrary to what the case-handler code suggested.** `_parseTechnical`'s `case 'hammer-on': case 'pull-off': note.isHammerPullOrigin = true;` (confirmed present, unconditionally, in the exact `v1.8.4` tag this project depends on) looked like it should mark both notes of a `<hammer-on type="start"/>`/`<hammer-on type="stop"/>` pair. Empirically, on both the real `32a-Notations.musicxml` file *and* a minimal hand-built two-note file with explicit `<technical><fret>/<string>` tab data on both notes (ruling out "missing tuning data" as the cause), **every hammer-on/pull-off note came back `isHammerPullOrigin: false, isHammerPullDestination: false`.** This is a genuine, previously-unflagged gap **specific to the MusicXML import path** — this doc's Phase 2 finding calling hammer-on/pull-off linkage "resolved, no longer open" was wrong and is corrected there.

  **Root cause, traced to a specific two-line ordering bug** (not a deep architectural conflict): `Beat.addNote(note)` ([`Beat.ts:808-814`](https://github.com/CoderLine/alphaTab/blob/v1.8.4/packages/alphatab/src/model/Beat.ts#L808)) snapshots the note into `noteStringLookup`, a `Map<number, Note>`, keyed by **whatever `note.string` holds at the moment the note is attached to its beat**: `if (note.isStringed) { this.noteStringLookup.set(note.string, note); }`. In MusicXML's element order, a note is attached to its beat (via `ensureBeat()` → `addNote()`) before `<notations><technical><string>` — the element that actually sets `note.string` — gets parsed. So the map is built using the note's still-default, unset string value, and nothing re-indexes it once the real value lands. `Note.finish()`'s hammer-pull linking (`Note.ts:897-904`) then calls `findHammerPullDestination()` ([`Note.ts:1114`](https://github.com/CoderLine/alphaTab/blob/v1.8.4/packages/alphatab/src/model/Note.ts#L1114)), which searches the next beat via exactly that stale map (`nextBeat.getNoteOnString(note.string)`), finds nothing, and clears the flag it couldn't confirm.

  Confirmed directly with a diagnostic: two sequential same-string notes both report the correct `note.string` value (`6`, `6`) when read directly, `beat.nextBeat` chaining is intact, but `beat1.getNoteOnString(6)` still returns `null` — proof the failure is the stale map, not the string value or beat linkage. GP's binary format has fret/string known at note-construction time, so `addNote()` always runs with an already-correct value there — which is exactly why the existing `gpConverter.test.ts` hammer-on test passes and this doesn't; the two import paths hit the same linking code with differently-ordered inputs.

  **Blast radius checked — one more confirmed-fine, one more confirmed-broken but harmless for this project.** `Note.ts`'s `findTieOrigin()` also calls `previousBeat.getNoteOnString(note.string)` — the same stale map — raising the question of whether ties (→ the `Continued` technique flag) share this bug too. Tested directly with a two-note tied pair on the same string/fret: **ties work correctly** (`isTieDestination: true`, `tieOrigin` set). `_parseTied` evidently does its own immediate linking at parse time rather than deferring to `Score.finish()`'s stale-map lookup, the same self-contained pattern `_parseSlide`/`_parseGlissando` use (an explicit `context.slideOrigins` map, checked earlier in this phase).

  **`palmMuteDestination`/`letRingDestination` chaining: confirmed broken too, but via a *different* bug, and it doesn't matter for this project.** Tested directly with a `<words>P.M.</words>`/`<words>LetRing</words>` + `<dashes>` file: `beat.isPalmMute`/`beat.isLetRing` come back correctly `true` (per the Phase 1 palm-mute finding above), but `note.isPalmMute`/`note.isLetRing` — the *per-note* fields `Note.finish()`'s destination-chaining logic actually reads (`if (this.isPalmMute) { ... }`, `Note.ts` lines 889, 878) — stay `false` on every note, so `palmMuteDestination`/`letRingDestination` never get set (not "set to the wrong note" — the chaining block never runs at all). Root cause here isn't the stale `noteStringLookup` map (that only explains hammer-pull) — it's that `MusicXmlImporter.ts` sets `isPalmMute`/`isLetRing` on the `Beat` (line 2574-2575) but never copies them down to each of the beat's `Note`s, a step GP's importer evidently does (GP-sourced palm-mute/let-ring destination-chaining is presumably fine, untested but consistent with GP's other working technique flags). **This one doesn't threaten this project's output**, though: `gpConverter.ts`'s `buildNote()` already reads `note.isPalmMute || beat.isPalmMute` (confirmed in the source, line 319) — a defensive OR that happens to route around this exact gap via the correctly-populated beat-level flag. `LetRing` isn't in `ESongNoteTechnique` at all, so its breakage has no consumer here either.

**Remaining still-open items after empirical testing:** whether `<staff-tuning>` is actually *emitted* by real-world export tools (MuseScore, Guitar Pro's "Export to MusicXML", TuxGuitar) remains unverified — the test-suite file proves the *format* and alphaTab's *handling of it* both work when the data is present, but says nothing about how often real exports actually include it. That's the one item that still needs files sourced from real tools rather than the spec's own conformance suite.

**Follow-up: real-tool export survey (2026-10-01).** Read exporter sources directly instead of sampling files. All alphaTab line refs below are the exact installed dependency (`@coderline/alphatab@1.8.4`, verified present in `SongConverter/node_modules`):
- **MuseScore** (`exportmusicxml.cpp`, `main`): tab staff emits `<staff-tuning>` per string (gated on `isTabStaff && instrument->stringData()`) *and* `<clef sign="TAB">`. Notation-only part emits neither — correctly skipped downstream, but there is no tab data to convert anyway. Palm-mute default begin text is the style default `"P.M."` (`styledef.cpp`), exported as `<words>P.M.</words>` + `<dashes type="start"/"stop">` via `textLine()` — exactly alphaTab's words-path shape (`MusicXmlImporter.ts` consumes `previousWords` only in the `dashes` case, literal `'P.M.'` match, line 2136). Works unless the user retypes the label.
- **TuxGuitar** (`MusicXMLWriter.java`, `helge17/tuxguitar` `master`): every non-percussion track gets 2 staves with staff #2 carrying `<staff-lines>` = string count, per-string `<staff-tuning>`, and `<clef sign="TAB">`. Palm mute is emitted *both* as bare `<words>P.M.</words>` (no `<dashes>`, so alphaTab's words path does **not** trigger) *and* as `<play><mute>palm</mute></play>`, which `_parsePlay` (line 2802) reads into `note.isPalmMute`. Net: works via the formal path.
- **Guitar Pro export: unverified at source level** (proprietary). Manual confirms a MusicXML export exists; a Dorico-forum thread mentions a "Tablature" export toggle (default on), suggesting tab staves are exported — but no proof of `<staff-tuning>` content. Needs one manual export test, not more research.
- **Sibelius/Finale/Dorico: unverified.** Lower priority: their typical exports are notation-only and correctly skipped; only their tab-staff exports would exercise this path.

### Phase 2 — Generalize the conversion core

`gpConverter.ts`'s `convertScore(score: alphaTab.model.Score)` already takes an alphaTab `Score`, not GP-specific data — per its own test file, scores are even built via the alphaTex importer in tests, not real `.gp5` bytes. A MusicXML entry point is close to:
```ts
export function convertMusicXml(bytes: Uint8Array): GpConvertResult {
    return convertScore(alphaTab.importer.ScoreLoader.loadScoreFromBytes(bytes));
}
```

**Findings:**
- Naming (`GpConvertResult`/`GpTrackResult`/`gpConverter.ts`) is still an open call — no technical blocker either way, purely a "how much churn to `main.ts` wiring is worth it" judgment. Not researched further since it has no right answer to discover.
- Part naming: `_parsePartName` reads `<part-name>` into `track.name` and `<part-abbreviation>` into `track.shortName` (`MusicXmlImporter.ts` lines 641, and the abbreviation case near it), plus `<score-instrument>`/`<instrument-name>` and `<midi-instrument>/<midi-program>` (lines 654, 713, 1389) for instrument/patch identity. **Empirically confirmed a real instance of the concern**, not just a hypothetical: the W3C-CG test suite's `71e-TabStaves.musicxml` (Phase 1) names four separate guitar parts all literally `"Guitar"`, plus `"Bass Guitar"`, `"Banjo"`, `"Lute"`, `"Ukulele"` — no lead/rhythm/solo hints anywhere. `determineRole()`'s `'bass'` keyword would correctly catch "Bass Guitar", but the four identically-named "Guitar" tracks would all fall through to positional guessing (first = lead, rest = rhythm), same as GP files with untitled tracks today. Not fixable at the code level — still needs a decision on whether that fallback is good enough or the keyword list needs tuning once more real files are seen.
- `isStringed`/tuning gating: confirmed via Phase 1's findings above — `isStringed` is a getter derived from `staff.tuning`, which the MusicXML importer only populates from `<staff-tuning>` or a TAB clef. **Empirically confirmed working** when that data is present (Phase 1's `71e-TabStaves.musicxml` run: `isStringed`/`showTablature`/`tuning` all correct for all 8 parts). So a mixed guitar+piano+vocal MusicXML file should correctly skip the non-fretted parts the same way `gpConverter.ts` already skips GP percussion tracks today — *provided* the guitar part actually carries tab data. A guitar part notated only in standard notation (no tab staff) would be misclassified as non-fretted and silently skipped; still open only insofar as how often real exports omit `<staff-tuning>`.
- **Hammer-on/pull-off linkage: corrected — this is a confirmed gap, not resolved.** The original pass at this phase read `_parseTechnical` setting `note.isHammerPullOrigin = true` (line 3587) and `isHammerPullDestination` being a getter resolved by the shared, format-agnostic `Score.finish()` pass, and concluded from that reading alone that `gpConverter.ts`'s existing `note.isHammerPullDestination` check would work unmodified for MusicXML notes. **Running real files through the actual installed dependency (`@coderline/alphatab@1.8.4`) disproved this**: every hammer-on/pull-off note in both a real W3C-CG test file and a minimal hand-built one (with explicit tab data, ruling out a tuning-data explanation) came back with both flags `false`. See Phase 1's empirical findings above for the full root cause (a stale-map ordering bug in `Beat.addNote()`/`noteStringLookup`, not a missing feature) — flagged here as a correction because this phase is where the wrong conclusion was originally drawn, and it's a direct, cautionary example of why source-reading needed the follow-up empirical pass rather than being trusted alone.

  **Fix options, now that the root cause is localized:** this is a small, well-understood ordering bug (a lookup map built from a value that's set later in the same parse pass), not a deep architectural gap — genuinely more tractable than palm-mute/slap/pop/harmonic, where the underlying data isn't there to read at all.
  - **Workaround entirely within this project's own code, no alphaTab changes:** after `ScoreLoader.loadScoreFromBytes()` returns, walk the score once and re-derive hammer-on/pull-off ourselves from `note.isHammerPullOrigin` + `note.string` + `note.beat.nextBeat`, independent of alphaTab's stale map. Lowest risk, same category as Phase 5's dead-note workaround (read around the bug at the boundary rather than touching the dependency).
  - **`patch-package`:** the actual fix is two lines, in `MusicXmlImporter.ts`'s `case 'string':` handler — re-set `note.beat.noteStringLookup` for the new string value right after `note.string` is assigned. Not currently a tool this repo uses (checked `SongConverter/package.json` — not present), so adopting it is a small new-tool decision, not just a patch file.
  - **Upstream:** a clean, minimal, two-line repro against an actively-maintained MPL-2.0 project with an open issue tracker — worth filing regardless of which local option is chosen, so the workaround doesn't need to be carried indefinitely. Doesn't block either local option; can happen in parallel.

  **Decided:** follow the same pattern already used across this project's other family repos (PsarcUtil, OpenSongChart, etc.) for upstream dependency bugs — patch locally for this project's own setup first, write up what the upstream PR would look like, then submit it once the local setup is confirmed working. Concretely here: `patch-package` with the two-line `noteStringLookup` re-index fix (not the from-scratch re-derivation workaround — the patch is smaller and fixes the actual bug rather than working around it), verified against this project's own test suite, then the same diff written up and filed against `CoderLine/alphaTab`.

### Phase 3 — Decide the scope for non-fretted parts

Unlike `.gp3/.gp4/.gp5` (which alphaTab's ecosystem treats as fundamentally tab-oriented), MusicXML is used at least as often for piano/vocal/orchestral scores with no tab data at all. `gpConverter.ts` today just skips (`skipped.push(trackName)`) anything that isn't `isStringed`.

**Findings** (corrects the first pass at this phase, which claimed no velocity/pedal data exists at all — that was wrong; the data exists, it's just coarser and structured differently than a MIDI performance capture):

- **Hand assignment (right/left) is structural, not a field.** `<attributes><staves>2</attributes>` triggers `track.ensureStaveCount(2)` (line 1700), creating two separate `Staff` objects under one `Track`. Each `<note>`'s `<staff>1</staff>`/`<staff>2</staff>` (line 2760) determines which `Staff`/`Bar` it's attached to — so a grand-staff piano part naturally splits into `track.staves[0]` (conventionally treble/right hand) and `track.staves[1]` (conventionally bass/left hand) before any conversion code runs. This is better ground truth than `pianoConverter.ts`'s current MIDI-path pitch-threshold guessing (below/above middle C) — it's the actual authored hand split, not an inference — with the caveat that it's a convention (staff 1 = treble), not an enforced rule, so a file with unusual staff/clef assignment could still mislead it.
- **Pedal marks exist, but as bar-level engraved marks, not a continuous signal.** `<direction><pedal type="start"/"stop"/"change">` is parsed (`_parsePedal`, line 2281) into `SustainPedalMarker { pedalType: Down/Up/Hold }`, pushed onto `bar.sustainPedals`. This is the same information a printed pedal line conveys — usable to derive a per-note `SustainActive` boolean (was a pedal marker set Down, with no subsequent Up, at or before this note's time?), but it's discrete engraved marks, not `pianoConverter.ts`'s continuous CC64-per-tick MIDI signal. Corrects my earlier claim that no pedal data exists at all.
- **Dynamics give a coarse, mappable velocity signal.** `<dynamics>` marks (`pp`/`mf`/`ff`/etc.) are parsed into an 8-level `DynamicValue` enum (`PPP`=0 .. `FFF`=7, plus rarely-used `PPPP`+/`FFFF`+ extremes) and assigned per-beat (`beat.dynamics`, line 3404-3409; also inherited across beats via `_currentDynamics` until the next mark). This is coarser than real MIDI velocity (8 discrete levels vs. 0-127) but directly mappable via a fixed table (e.g. evenly spaced 16-127), and — unlike raw velocity — it's authorial intent rather than performance noise, which may actually suit a notation-derived chart better. Corrects my earlier claim that no velocity-equivalent data exists.
- **Pitch-to-MIDI-number conversion is already done for you.** `note.realValue`/`note.calculateRealValue(...)` (used internally by the importer itself, e.g. in `_parseOrnaments`'s trill-direction check against B4=71) returns a standard 0-127 MIDI pitch number — directly usable as `SongKeyboardNote.Note` with no manual `<step>/<alter>/<octave>` math needed.
- **Piano-part detection has no MusicXML-native taxonomy to key off.** MusicXML 4.0 has a formal `<score-instrument><instrument-sound>` taxonomy (e.g. `keyboard.piano`) for exactly this purpose, but the importer doesn't parse it (no `instrument-sound` case found anywhere in the file). What *is* parsed is `<midi-instrument><midi-program>` into `track.playbackInfo.program`/`articulation.outputMidiProgram` (confirmed in Phase 2's findings) — the same GM patch number (0-7 = piano family) [[piano-midi-analysis]] already documents as the detection heuristic for the MIDI path. So MusicXML piano detection could reuse that exact heuristic/constant rather than inventing a new one — a real code/logic-reuse opportunity across the two piano paths, not just the guitar ones.
- **Voice-plurality within a staff should already work.** Piano writing is often polyphonic within one hand (two independent lines on one staff) — MusicXML represents this via multiple `<voice>` values on one staff, and `gpConverter.ts`'s existing `convertTrack()` already iterates `for (const voice of bar.voices) { for (const beat of voice.beats) ... }` generically, so this isn't guitar-specific code that would need piano-specific rework — **resolved, no longer open**, though not verified against a real polyphonic piano file.
**Still open (product decision, not more research) — piano only:** whether a piano MusicXML path is in scope for a first version at all. The technical picture is now much more favorable than the first pass suggested — hand-splitting is structurally *better* than the existing MIDI path, not worse — so this reads less like "extra unproven work" and more like "a plausible third `SongKeyboardNote` feed with its own (different, not missing) data characteristics," which may be worth weighing into the scope call.

### Lyrics/vocals — a separate, much smaller item, not bundled with piano

Corrected from the previous pass at this phase, which lumped lyrics into the piano scope question above as one combined "still open." They don't belong bundled — vocals are architecturally independent of both guitar and piano in the existing pipeline, and this is cheap enough to be worth including regardless of the piano decision, including in a guitar-only v1.

**Confirmed:** `SongVocal { Vocal: string, TimeOffset: float }` is already its own self-contained output shape. `PsarcConverter.cs` (lines 39-150) treats vocals as their own `ESongInstrumentType.Vocals` "part" with its own arrangement key, entirely separate from guitar/bass/keys extraction. The write path is fully generic — `main.ts:444`'s `files[`${part.Name}.json`] = JSON.stringify(part.Notes ?? part.Vocals, ...)` already handles a vocals-part the same way it handles a notes-part, naming the companion file after the part (`vocals.json`). Nothing about this mechanism is PSARC-specific.

**Feasibility for MusicXML:** alphaTab's importer already parses `<lyric>` into `beat.lyrics: string[]` per beat (Phase 1's `_parseLyric` finding — text + elision). Producing `SongVocal[]` is a walk over every track's beats emitting `{ Vocal: beat.lyrics[0], TimeOffset: <converted seconds> }` wherever present, written through the same generic `${partName}.json` mechanism already in `main.ts`. No new architecture, no new conversion concepts (unlike piano's hand-splitting/dynamics/pedal work) — genuinely small and self-contained.

**One real fidelity gap:** Rocksmith's own lyric convention (`vocal.Lyric.Replace('+', '\n')`, `PsarcConverter.cs:143`) encodes explicit line breaks, and `ChartUtil.FormatVocals` does syllable-aware line-wrapping on that. MusicXML's equivalent — `<lyric><syllabic>begin/middle/end</syllabic></lyric>`, marking whether a syllable continues a word — is explicitly unsupported by alphaTab's importer (`// case 'syllabic' not supported`, confirmed in Phase 1). So multi-syllable words would come through as separate lyric entries without the word-joining hint Rocksmith's format carries. Narrow, not a blocker.

**Still open:** which track's lyrics to use when a MusicXML file has multiple parts (always the melody/vocal-labeled part, or any part that happens to carry `<lyric>` data, including one whose notes are also being converted for its own instrument) — a small design call, not a research gap.

### Phase 4 — UI wiring

Mechanical, following the existing GP tab's pattern in [main.ts](../../SongConverter/src/main.ts) (`gp-input`, `gp-status`, `gp-metadata-form`, dynamic `import('./gpConverter')`).

**Resolved by reading [`ScoreLoader.ts`](https://github.com/CoderLine/alphaTab/blob/develop/packages/alphatab/src/importer/ScoreLoader.ts) and `MusicXmlImporter.ts`'s `readScore()`/`_extractMusicXml()` directly:**
- **`.mxl` needs no special handling.** `_extractMusicXml()` (line 255) always attempts `new ZipReader(this.data, ...).read()` first; if that throws (not a zip) it falls back to treating the raw bytes as plain-text XML (`IOHelper.toString(this.data.readAll(), ...)`, line 267). If it *is* a zip, it reads `META-INF/container.xml` to find the real MusicXML entry inside. This is pure content-sniffing — no file-extension logic anywhere, and no `fflate` involvement needed (alphaTab bundles its own `ZipReader`). `.musicxml`, `.xml`, and `.mxl` bytes can all go through the same `loadScoreFromBytes()` call gpConverter.ts already uses for GP files — `accept=".musicxml,.xml,.mxl"` is purely a UI-level file-picker hint, not something the parsing path branches on.
- **Bad/foreign file handling is inherited, not new.** `ScoreLoader.loadScoreFromBytes()` (line 84) tries every registered importer in turn — GP3-5, GP7/8, Capella, MusicXML, and **AlphaTexImporter as a catch-all** — catching `UnsupportedFormatError` between attempts and throwing a generic `UnsupportedFormatError('No compatible importer found for file')` only if all of them fail. This is the exact code path `gpConverter.ts` already calls for `.gp3/.gp4/.gp5` uploads today, so a MusicXML tab gets whatever error UX GP uploads already have — no new pre-check is required for parity, though it's worth confirming today's GP error message is actually informative before assuming it's good enough for MusicXML too (not researched further; a UI-review question, not a library one).
- **Still open:** whether a non-MusicXML, non-GP, non-alphaTex text file (e.g. a user mistakenly uploading an arbitrary `.xml`) gets swallowed silently by the `AlphaTexImporter` fallback and produces a confusing empty/garbage score rather than a clean error — would need an actual bad-file test to confirm either way.

### Phase 5 — Fallback handling for techniques MusicXML import won't populate

Palm-mute, vibrato, slap, pop, and (per the caveat) full harmonic detail are gaps in alphaTab's MusicXML import specifically — not gaps in the target `ESongNoteTechnique` flags, and not gaps in alphaTab's GP import. Silently emitting notes with those flags always unset would be a quiet accuracy regression relative to the GP and PSARC paths.

**Findings — palm-mute is better off than this section originally concluded.** The original framing here assumed palm-mute needed a speculative text-pattern fallback like slap/pop. Phase 1's follow-up found alphaTab already has a working path for it: `<words>P.M.</words>` + `<dashes>` (the actual "drawn line" mechanism real tools use, per the MuseScore forum thread) sets `beat.isPalmMute`, and `gpConverter.ts` already reads that field. So palm-mute doesn't need a fallback built — it needs the same "does the real tool emit the exact matching text" verification every other real-file-dependent item in this doc needs, not new code.

Slap, pop, and harmonic type are a different story: no working path surfaced for any of them. The MuseScore thread's point stands specifically for those — MusicXML's formal playback-technique elements aren't the mechanism real tools use, and unlike palm-mute, no text+dashes (or equivalent) fallback path exists in the importer for slap/pop, and harmonic's `<technical><harmonic>` case is a confirmed no-op regardless of how it's authored. A regex fallback for these would need per-export-tool tuning discovered empirically, a materially bigger investment than "one fallback regex." Combined with the confirmed `<notehead>x</notehead>` dead-note gap ([#2866](https://github.com/CoderLine/alphaTab/issues/2866)), the honest framing is now narrower than before: **slap, pop, and harmonic type remain a real accuracy gap for a first version; palm-mute and dead notes both turned out to have working paths (dead notes needs a small local fix, palm-mute needs nothing extra); vibrato works for the standard `<wavy-line>` case.**

**One targeted exception worth calling out separately: dead notes are cheaply fixable without waiting on upstream.** Phase 1's OSMD cross-validation found alphaTab *does* correctly capture the notehead shape even though it doesn't act on it — confirmed via the public model: `Note.style?.noteHead: MusicFontSymbol` (`alphaTab.d.ts` line 13122/13291) is set to `MusicFontSymbol.NoteheadXBlack` (or a duration-appropriate X variant) for an `<notehead>x</notehead>` note, per `MusicXmlImporter.ts` line 3185. So `gpConverter.ts`'s `buildNote()` could check `note.style?.noteHead` against the known X-notehead symbols and OR in `Technique.FretHandMute` itself — a small, local workaround, not a fork of alphaTab or a wait on #2866. This is a meaningfully different, lower-risk case than palm-mute/slap/pop/harmonic, where no such workaround surfaced (the underlying data genuinely isn't there to read).

**Still open (product decision, not research) for the rest:** document vibrato-from-non-wavy-line-sources/slap/pop/harmonic-type as known limitations for v1 and revisit with real per-tool patterns once Phase 1's file survey shows which gaps actually matter for the files users upload, vs. building speculative fallbacks now. The status-line-surfacing idea (mirroring `gpStatus`/`psarcStatus`'s skipped-track reporting) still stands as the cheaper, honest middle ground for those — flag what's missing rather than silently guessing or silently omitting.

### Phase 6 — Testing and fixtures

`gpConverter.test.ts` avoids needing binary `.gp*` fixtures by building scores through alphaTab's alphaTex text-based importer instead.

**Findings:**
- alphaTex's own syntax reference confirms rich effect markup: bend (`{b (...)}`), hammer-on/pull-off (implicit from consecutive frets on a string, matching `gpConverter.test.ts`'s existing `0.6{h}` example), tap, multiple harmonic types (artificial/tapped/pinch/semi/feedback), slide, palm-mute, staccato, let-ring, and vibrato. So **alphaTex can fully exercise `convertScore()`'s note-mapping logic** — the part shared between GP and MusicXML — the same way `gpConverter.test.ts` already does, with zero binary fixtures needed for that layer.
- What alphaTex *cannot* test is the MusicXML-parsing step itself (`MusicXmlImporter.ts`'s XML-to-`Score` conversion) — that needs real `.musicxml`/`.mxl` input, since alphaTex bypasses XML parsing entirely by construction.
- Checked for a fixture-licensing precedent already in the repo: **none needed, because there isn't one to follow.** Both existing SongConverter test files (`gpConverter.test.ts`, `tempoMap.test.ts`) build all test data synthetically (alphaTex strings, hand-built MIDI event arrays) — no binary `.gp*`, `.mid`, or `.psarc` fixture files are committed anywhere in `SongConverter`. The established pattern is "don't commit real song files," which resolves the licensing question by avoiding it rather than answering it — a small, hand-authored `.musicxml` fixture (a few notes, not a real song, analogous to alphaTex's tiny test strings) is the pattern to follow, not excerpting a real file found during Phase 1's survey.
